## Critical Restrictions
- NEVER run `rm -rf` except in tmp/ without explicit human confirmation.
- Do not attempt to run `rm -rf` in the middle of a long job EXCEPT in folder "tmp/" within this working directory you were launched in. Complete the job first, then tidy up afterwards, to reduce interruptions.
- NEVER alter system configurations, `.bashrc`, `.bash_profile`, `.bash_aliases`, or install global apt packages.
- NEVER access or create `.env` files containing deployment API keys.
- NEVER run commands using the `--dangerously-skip-permissions` flag.
- **NEVER change file permissions without asking me first, every single time.** No `chmod`, no `chown`, no `sudo`. Ask, name the exact files, and wait -- a blanket "yes" to one chmod is not a standing permission for the next one. `.claude/settings.json` denies these three commands outright, but as with the `/tmp` rule above, Bash can't be perfectly restricted by permission patterns, so this line is the actual backstop. The one time this came up (2026-08-17) the fix was legitimate -- `.gh-runtime/bin/gh` and `.node-runtime/node/bin/node` had been extracted without their execute bit, which is why the JS test suite had silently not been running -- and it was still Helen's call to make, not mine.
- NEVER read, write or execute above the folder you're in.
- NEVER read, write or execute in `~` (my home directory) or anywhere outside this project folder, for any reason -- if Claude Code config/settings storage is ever needed, it belongs in this project's own `.claude/` folder, never `~/.claude/`.
- NEVER read, write or execute using the system `/tmp` directory (an absolute path starting `/tmp`). Use this project's own `tmp/` folder for all scratch and temporary files. Settings-level deny rules block this for the Read/Write/Edit tools, but Bash can't be perfectly path-restricted by permission patterns -- this rule is the actual backstop.
- NEVER use `$CLAUDE_JOB_DIR` or any path under `/home/helen/.claude/jobs/` as a scratch location, even though background-job tooling suggests it by default. All scratch/temporary files -- including any helper script written to a file specifically to avoid a shell-quoting/brace-expansion warning -- belong in this project's own `tmp/` folder, always.

  - Anything longer, or containing single quotes: write it to a file in `tmp/` (or the relevant repo's tmp) with the Write tool, then run it as a plain file argument, e.g. `python3 tmp/fix_thing.py`. Also statically analyzable, matches the existing `Bash(python3 *)` allow rule.
  Diagnosed 2026-09-07 after this looked like a permission-state regression but was actually just heredoc usage creeping in.
- **Never prefix a Bash command with `cd /workspace;` (or any `cd`).** The Bash tool already runs with the working directory set to the project root by default -- there is nothing to `cd` into. All it does is break every prefix-based allow rule you have: `Bash(grep *)` matches a command that STARTS with `grep`, and `cd /workspace; grep ...` starts with `cd`, so it matches nothing and always prompts, in every permission mode, no matter how good the allow-list is. Diagnosed 2026-09-07 inside the devcontainer, where a session had picked up the habit and every single command was prompting despite auto mode being on and the allow-list being fully present (it's part of the bind-mounted project directory, same as on the host).
- **Never glob a file-path argument to a read command (`grep -rl "x" dir/*.md`, `cat some/*.txt`, etc.) -- point the command at the directory and let it recurse, or list files explicitly.** Same underlying mechanism as the heredoc rule above: the permission checker statically verifies a command's file-path arguments stay inside the working directory, but a shell glob expands at runtime, so the actual list of files being read isn't known until after the check would need to run -- it can't be verified, so it always hard-asks, regardless of mode or allow-list, exactly like unanalyzable stdin. Most tools that take a glob also take a bare directory and recurse into it themselves (`grep -r "x" dir/` needs no `*.md` at all) -- that's a single static path, fully analyzable, and actually matches an allow rule. Diagnosed 2026-09-07 alongside the `cd` prefix issue, same session, same symptom.
- **Never build a multi-line commit message or PR body with `"$(cat <<'EOF' ... EOF)"`.** Third variant of the same heredoc problem, easy to miss because it LOOKS like a normal quoted argument rather than an obvious heredoc: the value only exists once the command substitution actually runs, so the checker can't verify it ahead of time and always hard-asks -- `git commit -m "$(cat <<'EOF' ...)"` and `gh pr create --body "$(cat <<'EOF' ...)"` both have this problem, no matter how good the allow-list is. Write the message/body to a file in `tmp/` with the Write tool first, then pass the file: `git commit -F tmp/commit-msg.txt`, `gh pr create --body-file tmp/pr-body.md` (plus the rest of the usual flags). Both are then a single static command with no runtime-computed content, so they're actually analyzable and can be allow-listed. Diagnosed 2026-09-07 after Helen flagged a `gh pr create` prompt as one of "a handful" of similar ones -- this exact pattern had been used for essentially every commit and PR all session.
- **One command per Bash call. Never chain with `;` or `&&` to save a round trip.** Helen, 2026-09-08: *"Please write complex commands out one at a time, so they can be statically analysed."* A chained command is checked as a whole, so `grep ... && node ...` matches neither the `Bash(grep *)` rule nor the `Bash(node *)` one and hard-asks -- the same prefix-matching mechanism as the `cd` rule above, and it fires even when every part on its own is allow-listed. Two calls cost a round trip; one chained call costs an interruption, and that lands on Helen rather than on you.
- **Anything with a pipe, a variable, a substitution or a loop goes in a script in `tmp/`.** Her rule, same day: *"if they take or emit variables, please write a script in tmp/ so you don't need to request permissions from me."* A pipeline's later stages, any `$VAR` and any `for` body are runtime-computed, so the checker cannot see what will actually run and will not allow-list it -- identical to the heredoc and glob cases. Write it with the Write tool and run the file: `sh tmp/thing.sh`, `python3 tmp/thing.py`, `ruby tmp/thing.rb`. One static path, analyzable, and with a second payoff: the script is a record of exactly what was measured, which a one-off pipeline never is.
- **`--body-file`, never `-b "..."`, for any `gh` body or comment.** Helen, 2026-09-08. The same shape as the commit-message rule above, and easy to miss because a quoted string looks innocent -- but a multi-line body full of backticks and quotes is precisely the argument the checker cannot verify, and backticks inside a double-quoted shell string are command substitution as well, so it is a correctness risk and not only a friction one. Write the body with the Write tool and pass `--body-file tmp/whatever.md`. Applies to `gh issue comment`, `gh issue create`, `gh pr create` and `gh pr edit` alike.
- **All of these rules are one rule, and it is worth stating once.** The permission checker proves, before anything runs, that a command touches only the working directory. It can do that only for a command whose text is its whole meaning. Every rule above names a way of hiding meaning from it -- on stdin, behind a glob, behind a substitution, behind a `cd`, behind an `&&`, behind a variable -- and the cost is never a refusal, always an interruption to Helen. **When a command needs to be clever, put the cleverness in a file and run the file.**
