# Claude Code Rules for Jekyll

**This file is the RULES. It is loaded into every session, so it stays short.**
The reasoning, the dates, the rulings and the stories of what broke live in
`model_instructions/DECISIONS.md`, which is the journal; how the machinery
works today lives in `model_instructions/MANUAL.md`. A `DECISIONS §n` here
points you at the argument if you need it. **Do not re-open a settled question
without reading its section there first** — that is the thing Helen least
wants.

Where a rule names a hook, the hook enforces it and the argument has moved.
Where a rule has no hook, the paragraph explaining it is the only enforcement
there is, and it stays.

- **NEVER change file permissions without asking me first, every single time.** No `chmod`, no `chown`, no `sudo`. Ask, name the exact files, and wait -- **a blanket "yes" to one chmod is not a standing permission for the next one.** `.claude/settings.json` denies all three, but Bash cannot be perfectly path-restricted by permission patterns, so this line is the actual backstop. DECISIONS §11.
- NEVER read, write or execute above the folder you're in. **One exception, read-only: `/workspace/.node-runtime`** (Helen's grant, 2026-09-21). It is spelled `additionalDirectories` plus an `Edit(...)` deny, because a `Read(//path/**)` allow rule does NOT override `blockReadsOutsideWorkingDirectories`. **A settings edit does not reach a RUNNING session** — the working-directory set is fixed at session start, so a new grant needs `/add-dir` to go live today. DECISIONS §11.
  - **`Read(//dev/null)` and `Edit(//dev/null)` stay.** A session called them inert by running the Read TOOL and generalising; a Bash redirection is a different path and `>/dev/null` works. **Never conclude a permission rule does nothing from one tool's refusal** — a rule and a block are different mechanisms, and exercising one says nothing about the other.
- NEVER read, write or execute in `~` (my home directory) or anywhere outside this project folder, for any reason -- if Claude Code config/settings storage is ever needed, it belongs in this project's own `.claude/` folder, never `~/.claude/`.
- NEVER read, write or execute using the system `/tmp` directory (an absolute path starting `/tmp`). Use this project's own `tmp/` folder for all scratch and temporary files. Settings deny this for Read/Write/Edit, but Bash cannot be perfectly path-restricted -- this rule is the backstop.
- NEVER use `$CLAUDE_JOB_DIR` or any path under `/home/helen/.claude/jobs/` as a scratch location, even though background-job tooling suggests it by default. All scratch files -- including a helper script written to a file to avoid a quoting warning -- belong in this project's own `tmp/` folder, always.

## Git workflow
- If we're starting new work, and we're currently on main, please check out a new branch.
- **Update `main` without checking it out: `sh scripts/git-fetch-main.sh`, then `git merge origin/main`.** It updates `origin/main` only, touches no checked-out branch, works everywhere and never prompts. **Never check `main` out to "fix" a refusal** — git refusing to fetch into a checked-out branch is protecting the same invariant this rule exists for. DECISIONS §1, §11.
- Commit freely without asking.
- **NEVER commit or merge directly onto `main`, for any reason, in ANY repo in the tree** -- including the nested private drafts repos, which are separate repos with their own `main`. `.claude/hooks/guard-main-branch.py` enforces it. Everything else on `main` is untouched: reading, fetching, branching, checking out, pushing an existing commit.
- **THE AGREED WORKFLOW. Four steps, and only one is Helen's.**
  1. Claude works on a branch, then **pushes it and opens the PR with no ask at all**: `sh scripts/git-push-agent.sh <branch>:<branch>`, then `sh scripts/gh-write.sh pr-create <repo> <branch> "<title>" tmp/body.md`. This holds in all three repos.
  2. **Helen reviews the PR and merges it. That is all she does.** Claude opening a PR is not, and never becomes, authorization to merge it.
  3. Claude runs `sh scripts/git-fetch-main.sh`, deletes the merged branch local and remote (`sh scripts/git-push-agent.sh :<branch>`), and branches afresh.
  4. Repeat. Claude is never on `main`, so the hook should never actually fire.
- **Pushing runs as a separate GitHub identity, `DeckOfPandas-agentic-claude`, over HTTPS — never `origin`, which is SSH and dies in the container.** You never handle the token: the three wrappers pass `scripts/git-credential-agent-token.sh` to git per invocation. `sh scripts/git-push-agent.sh <branch>:<branch> [repo]`, `sh scripts/git-clone-agent.sh <repo> [dir]`, `sh scripts/git-fetch-agent.sh <dir> <repo> [ref]`. **Never build a URL with the token in it** — a clone stores it in `.git/config` and `git remote -v` prints it; `guard-token-expansion.py` refuses the shape. DECISIONS §11.
  - **Commit AUTHORSHIP does not change.** Commits stay authored as Helen with the usual `Co-Authored-By: Claude` trailer; only which account talks to GitHub changes. Do not set `user.name`/`user.email` to the bot anywhere.
  - **Read `.user.login` off what a write returns** (`scripts/gh-write.sh` prints it) rather than assume which account GitHub recorded.
- **Pushing needs no ask, in any of the three repos. Pushing is not merging**: `main` only ever moves via a PR Helen merges. A commit sitting unpushed on one disk exists in exactly one place, which is the real risk.
- **Every PR's base is `main`. Never stack a PR on another PR's branch, and read a PR's `state` before pushing to a branch whose state you have not checked since you last looked — including your own.** Both cost the live site on 2026-09-11: GitHub moves a stacked PR onto `main` only when its base BRANCH is deleted, not when the base's PR merges, and a merged PR's branch still accepts a push that reaches nothing. If a second piece needs the first's tooling, say "merge #A first" and rebase onto `main` once it has. `sh scripts/gh-read.sh repos/DeckOfPandas/<repo>/pulls/<N> --fields state,merged` answers it in one call. **Merging is Helen's, so a branch's state can change under you at any moment.** DECISIONS §11.
- **Say when you have merged, if it is easy.** A merge changes which branch is current, and being told beats finding out. Equally: if Claude has been told nothing, it should check rather than assume.
- **NEVER run `git reset --hard` (or `git checkout --` / `git restore` over a dirty tree, or `git clean -fd`) without asking me first, every single time.** `.claude/hooks/guard-destructive-git.py` enforces it whenever `git status` is not clean, and names what would be lost. These discard uncommitted work with no undo and no reflog entry. **Check `git status` first and say what it shows.** If something needs discarding and I am not around, `git stash -u` instead: it is reversible. DECISIONS §11.
- **Check `git branch --show-current` immediately before every `git commit`, IN A SEPARATE TOOL CALL.** Not at the start of the task, and not in the same shell command as the commit — that shape has already put commits on `main`:

      git branch --show-current      <- the check
      git add ...
      git commit -F ...              <- already done by the time it printed

  **A check that cannot stop the thing it is checking is a narration, not a check.** Run it, read the answer, then decide.

  **The question it answers is not only "am I on `main`" but "am I still where I left off".** `/workspace` is a bind mount, so another session — or Helen — switching branch moves the ground under you with no signal. `session-ground-truth.py` reports this at session start; re-check after any long gap. DECISIONS §11.
- **ALWAYS tag issues in commit messages.** `Fixes #N` / `Closes #N` for every issue a commit resolves; `Towards #N` / `See #N` in the body for one it only touches. **BUT A COMMIT'S KEYWORD DOES NOT CLOSE THE ISSUE ON A PR THE AGENT ACCOUNT OPENED — THE PR DESCRIPTION IS WHAT CLOSES IT.** So keep the commit trailers for the history, **and put every closing line in the PR description too, one keyword per issue per line, never a comma list** (a keyword covers only the one reference after it). Read the issue list after the merge. Do this at commit time, while a message can still be rewritten. When summarising work, list the issue numbers involved. DECISIONS §11.
- **A bare `#N` only resolves within its OWN repository.** The nested private drafts repos have their own (empty) trackers. Cross-repo references need the full form: `Towards DeckOfPandas/helen-triages#314`.

## Proofreading -- Helen is the last judgement before a recipe publishes
- **If you edit a recipe or drink file, set `meta.proofread: false` in the SAME commit.** Helen proofreads every one by hand before it goes live; if Claude changes the file afterwards, her proofread no longer covers what is in it. **This applies to any change, including ones that look safe.**
- **THE GATE IS TWO FLAGS AND IT FAILS CLOSED: a recipe or drink publishes only if it says `awaiting_fix: false` AND `proofread: true`.** An explicit pass on both is the only thing that lets a page through. Either flag missing, the old hyphenated `awaiting-fix`, or a quoted string: all held back, and all break a test, which stops the build. **Never write the hyphenated form** — Liquid parses `page.meta.awaiting-fix` as SUBTRACTION, so a template asking whether a page is flagged gets arithmetic and publishes it. The mechanism is `_plugins/publish_gate.rb`, and its build-log line names which flag held each page back. DECISIONS §4.0.
- `tests/test_front_matter.py::test_agent_edited_recipes_are_not_marked_proofread` enforces it by reading git history: if a recipe's newest commit carries a `Co-Authored-By: Claude` trailer, the file must say `proofread: false`. Drinks have the same test.
- **The exception is Helen's to grant, not yours.** If she has reviewed the change herself, line by line, then she was the last judgement even though an agent's commit wrote the bytes. Move `BASELINE_COMMIT` (or `COCKTAIL_BASELINE_COMMIT` in `tests/test_cocktails.py`) forward, in a commit of its own, quoting her grant, and prove it afterwards by running the test with the old value and watching it name the files. **Never move it to make a red test go green.** **The cheapest shape: if she reads the rendered pages ON THE BRANCH before it merges and says so, flip the flags back in a second commit and move the baseline in a third — nothing ever leaves the live site.** DECISIONS §4.0.

## GitHub Issues and Pull Requests -- read/write, never merge, never repo settings
- Claude may READ, RAISE, CLOSE, REOPEN, COMMENT ON, LABEL and ASSIGN issues, and OPEN pull requests, on `DeckOfPandas/helen-triages`, `helen-triages-food-private` and `helen-triages-cocktails-private`. **Those three repositories and no others. That is the entire permission.**
- **One credential: `AGENT_GH_TOKEN`.** It is the agent account's classic `repo`-scoped PAT and works on all three repos. `DECISIONS.md` §11 holds the measured scope tables for the retired `GH_TOKEN`; don't re-derive them, they describe a credential that no longer exists.
- **MERGING IS PREVENTED BY NOTHING BUT THIS LINE, SO TREAT IT AS ABSOLUTE.** A classic `repo`-scoped token held by a collaborator CAN merge. Never merge a pull request, never close one as merged, never approve one. Never change repository settings, secrets, Actions, webhooks or collaborators. Never act on any other repository. **Pushing a branch has never been, and does not become, a way to move `main`.**
- **NEVER CREATE ISSUES OR PRs IN A BURST.** Twenty issues and two PRs in under an hour got the agent account flagged as spam on 2026-09-14, and GitHub hid **everything it had ever written** — profile, PRs, issues, all 404 to everyone but the account itself, while the API cheerfully reported them open and normal. The replacement account is younger still, so this applies with more force, not less.
  - **A batch of issues is ONE issue with a checklist**, never one issue per file, and never more than a handful of creations in an hour. Separate issues are fine **when Helen asks for them, one at a time, 10–30 seconds apart**. A foreground `sleep` is refused, so wait with `sleep 20` in the background and create the next when its notification arrives.
  - **When Helen says she cannot see something the API says exists, believe her first** and check the page logged out: `sh scripts/github-public-status.sh <url>`. A public URL returning 404 while the API returns 200 is the flag, and no amount of re-listing from the same token will show it. The branches stay visible, so the way through is the compare link: `https://github.com/DeckOfPandas/<repo>/compare/main...<branch>`. Only Helen can appeal to GitHub Support.
- **DON'T PROBE A TOKEN'S SCOPE OR ITS PRESENCE -- USE IT AND READ THE STATUS CODE.** A 401 or 403 is the answer and never renders the value; in Python, `os.environ["AGENT_GH_TOKEN"]` raises a clear `KeyError`. `GET /user/repos` does NOT reveal a fine-grained token's scope — it lists what the ACCOUNT owns. **Do not treat a 403 as a problem to route around.**
- **Never attempt to broaden access beyond the above.** No `gh auth login`, no wider token, no extra scopes or repositories, no second credential. If something genuinely needs a permission not covered here, say so and stop -- Helen will do it by hand.
- **Never print, echo, log or commit the token**, and never write it into a file in this repo. **NEVER PUT A SECRET'S NAME IN AN `echo` OR `printf` AT ALL -- there is no safe form and no exception to remember.** Not `${TOK:-x}`, and not `${TOK:+set}` or `${#TOK}` either, which cannot leak and are still refused: from the outside a command with a secret's name in it is indistinguishable from a leak until someone has run the rule in their head, and Helen should not have to. Using `${TOK}` where it is CONSUMED rather than printed is fine and always was. `.claude/hooks/guard-token-expansion.py` enforces all of this. DECISIONS §11.
- **FOR `gh`, USE THE WRAPPER AND DON'T NAME THE TOKEN AT ALL: `sh scripts/gh-agent.sh <args>`.** Run it via `sh`, so it needs no execute bit and so no chmod. It deliberately does not check the credential is present -- use it and read `gh`'s own 401.
- **CLOSE AN ISSUE WITH A COMMIT TRAILER, NOT THE API, WHENEVER A TRAILER CAN DO IT.** Helen's standing preference: a trailer ties the closure to the commit that earned it. Reach for the API only where a trailer genuinely cannot work -- the clear case being work in a nested private drafts repo, since a cross-repo trailer does not close or even cross-reference a public issue.
- Closing an issue is a real action on a shared, outward-facing thing: **say which issues you are about to close and why before doing it**, unless Helen has just told you to close them. That applies to a trailer too -- name them before pushing, while the message can still be rewritten.

## Normal workflow
- If you need a scratch temporary folder, create one in this project folder and add it to .gitignore.
- Don't delete handover or jobs list documents.
- **NEVER remove or tidy up an agent's worktree under `.claude/worktrees/`, even once its branch is merged and deleted.** They hold the branch, the scratch files and the screenshots each helper worked from, which is the only record of HOW a piece of work was measured once the branch is gone. `git worktree remove`, `rm -rf` on one, and `git worktree prune` are all Helen's. This does not stop you deleting a merged BRANCH — `git branch -d` refusing one a worktree holds is not a problem to solve.
- **CLONE THE TWO PRIVATE DRAFTS REPOS INTO A FRESH WORKTREE WHENEVER YOU WANT THEM. NO ASK, ANY SESSION, ANY TIME.** Cloning is READING: nothing is written to a remote, and both folders are gitignored here.

      sh scripts/git-clone-agent.sh helen-triages-cocktails-private _cocktail_drafts
      sh scripts/git-clone-agent.sh helen-triages-food-private _food_drafts

  **WITHOUT THEM TWO THIRDS OF THE SUITE DOES NOT EXIST**, and it reports green rather than absent: 10,660 tests collected in a bare worktree against ~30,900 with both clones, and the skip count *falls*, because most of the missing checks are parametrised per file and are never created at all. **A green `pytest` in a bare worktree is not evidence about the drinks or the drafts** — `conftest.py` says so at the end of every such run. MANUAL §9.1 has the wrapper detail.
- **One `pytest` at a time**, never two.
- **Never run multi-line scripts via a Bash heredoc** (`python3 - <<'PY' ... PY`). The body arrives on stdin, which the permission checker cannot see, so it can NEVER be allow-listed.
  - **EVERY python/ruby/node/perl program goes in a file, however short.** Write it to `tmp/` with the Write tool and run it as a plain file argument: `python3 tmp/fix_thing.py`. **There is no short-enough and no quote-free-enough** — an inline program is opaque by construction, and `.claude/hooks/guard-inline-script.py` refuses every `-c`/`-e` form. **It still asks Helen, on purpose**, so reach first for a committed allow-listed wrapper; a `tmp/` script is for the genuine one-off.
- **Never prefix a Bash command with `cd`, and never use `git -C <path>`.** The Bash tool already runs in the worktree root. Allow rules match a command's PREFIX, so `cd /workspace; grep ...` and `git -C /path status` match nothing and always prompt. **Lowercase `git -c key=value` is a different flag and stays allowed** — it is how every `git-*-agent.sh` passes the credential helper.
- **Never glob a file-path argument to a read command** (`grep -rl "x" dir/*.md`). A glob expands at runtime, so the file list is unknown when the check would need to run. Point the command at the directory and let it recurse: `grep -r "x" dir/`.
- **Never build a commit message or PR body with `"$(cat <<'EOF' ...)"`.** Write it to a file and pass the file: `git commit -F tmp/commit-msg.txt`, `--body-file tmp/pr-body.md`.
- **`--body-file`, never `-b "..."`, for any `gh` body or comment.** Backticks inside a double-quoted shell string are command substitution, so this is a correctness risk and not only a friction one. **`gh pr edit` fails on this token** (GraphQL, wants `read:org`) — change a PR's body with `sh scripts/gh-write.sh pr-body <repo> <N> tmp/whatever.md`.
- **One command per Bash call. Never chain with `;` or `&&` to save a round trip.** A chained command matches neither part's allow rule even when both parts are allowed alone.
- **Anything with a pipe, a variable, a substitution or a loop goes in a script in `tmp/`.** Run the file: `sh tmp/thing.sh`, `python3 tmp/thing.py`. Second payoff: the script is a record of exactly what was measured, which a one-off pipeline never is.
- **All of these rules are one rule, and it is worth stating once.** The permission checker proves, before anything runs, that a command touches only the working directory. It can do that only for a command whose text is its whole meaning. Every rule above names a way of hiding meaning from it -- on stdin, behind a glob, behind a substitution, behind a `cd`, behind an `&&`, behind a variable -- and the cost is never a refusal, always an interruption to Helen. **When a command needs to be clever, put the cleverness in a file and run the file.**
- **A HOOK ENFORCES THAT ONE RULE, SO AN UNANALYSABLE COMMAND IS REFUSED RATHER THAN PUT TO HELEN** -- `.claude/hooks/guard-unanalyzable-bash.py`. **The point is who pays**: a prompt is not a refusal, it is an interruption, and it lands on Helen; a denial lands on the session, which can write the script and carry on. Ten refused shapes: a heredoc; `$(...)` or backticks; a leading `cd`; `git -C`; a leading `NAME=value`; a pipe; `&&`/`||`/`;` chaining; a glob in an argument; an unquoted `(` or `)`; and a quoted `[`, `]` or `|` given to `sh scripts/...`.
  - **It allows** redirection to a static path, `2>&1` and `>/dev/null` included (a redirection names its file; only a PIPE hides a later stage); anything inside quotes for `&&`, `||`, `;`, `|` and globs; and a bare `$VAR`, left to `guard-token-expansion.py`.
  - **The one asymmetry to remember: `$(...)` and backticks are NOT exempt inside DOUBLE quotes**, because the shell expands them there -- so prose about substitution goes in single quotes.
- **Never `sed`** (`.claude/hooks/guard-sed.py`) and **never `awk`** (`.claude/hooks/guard-awk.py`, covering `gawk`/`mawk`/`nawk`). Both are inline programs in a quoted argument the checker cannot see into, where `print > "file"` writes, `system()` runs anything and `gawk -i inplace` edits in place. Use Python in a file, as for everything else.
- **The routine calls are allow-listed, so they do not prompt.** `.claude/settings.json` allows: the `gh` wrapper's `issue list`/`view`/`comment`/`create`/`edit` and `pr list`/`view`/`diff`/`create`/`comment`/`repo clone`; **`sh scripts/gh-read.sh <endpoint> [--fields a,b | --each a,b | --jq <expr>] [--paginate]`** for every REST read (prefer `--fields`/`--each`, which build the jq inside the script — a bracketed `--jq` makes Claude Code ask; GET only, three repos only, and never `gh-agent.sh api` for a read, which prompts because `api` is also the door to a merge); **`sh scripts/gh-write.sh pr-create|pr-body|comment`** for the three routine REST writes; `sh scripts/github-public-status.sh <url>`; the three git wrappers; `sh scripts/git-fetch-main.sh` then `git merge origin/main`; `git branch --show-current`; `git add -- <paths>` (the `--` is what makes it safe: every later word is a path, never `--chmod`); `python3 scripts/verify.py`; `node --test`; read-only git (`status`, `diff`, `log`, `show`, `blame`, `ls-tree`, `check-ignore`); `git commit -F`; and `scripts/browser/`'s `install.sh`, `build.sh`, `serve.sh`, `shoot.sh`, `crop.sh`, `styles.sh`, `gaps.sh`, `click-crop.sh`. **`pr merge` and `pr review` are in the DENY list**, and a deny cannot be overridden by an allow.
- **AN ALLOW RULE IS ONLY AS NARROW AS WHAT IT LETS THROUGH. Before adding one, ask what the prompt was the last guard of.** A rule ending ` *` accepts ANY further argument: `git fetch --upload-pack=`, `git ls-remote --upload-pack=`, `git clone --template=` and `node --import` all RUN a program, and `curl -o <path>` WRITES a file anywhere — ask what an option can write as well as what it can run. Prefer an exact command, or a committed wrapper that checks its own arguments and has its refusals proved in `tests/test_agent_wrappers.py`, which pins which open-ended rules exist.
- **A COMMAND THAT BUILDS A PATH AT RUN TIME GETS A WRAPPER, NOT A PROMPT.** `-F body=@tmp/x.md`, `curl -o <file>` and their kin read or write a path the checker cannot see, so no allow rule can vouch for them. The answer is the `gh-read.sh` shape: a committed script under `scripts/` that takes only arguments it understands and refuses the rest.
- **A PROMPT HELEN HAS STOPPED READING GUARDS NOTHING -- SO EVERY BASH `description` SAYS WHAT A CALL TOUCHES.** Name what is read or written and where (*"Read-only GitHub GET: PR #1091's state. No local files read or written."*), never just the goal (*"Check whether the PR is merged"*). A prompt is only a guard while it is read, so each one must be both rare and legible — and a call you expect to ask should be one you would defend to her.
