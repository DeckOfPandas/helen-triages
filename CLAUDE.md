# Claude Code Rules for Jekyll

## Environment Constraints
- OS: Ubuntu/Debian inside Windows Subsystem for Linux (WSL).
- Environment: Local Jekyll development.
- Target Directory: ONLY operate within this folder. Do not traverse to `../` or `/mnt/c/`.

## Critical Restrictions
- NEVER run `rm -rf` except in tmp/ without explicit human confirmation.
- Do not attempt to run `rm -rf` in the middle of a long job EXCEPT in folder "tmp/" within this working directory you were launched in. Complete the job first, then tidy up afterwards, to reduce interruptions.
- NEVER alter system configurations, `.bashrc`, `.bash_profile`, `.bash_aliases`, or install global apt packages.
- NEVER access or create `.env` files containing deployment API keys.
- NEVER run commands using the `--dangerously-skip-permissions` flag.
- **NEVER change file permissions without asking me first, every single time.** No `chmod`, no `chown`, no `sudo`. Ask, name the exact files, and wait -- a blanket "yes" to one chmod is not a standing permission for the next one. `.claude/settings.json` denies these three commands outright, but as with the `/tmp` rule above, Bash can't be perfectly restricted by permission patterns, so this line is the actual backstop. The one time this came up (2026-08-17) the fix was legitimate -- `.gh-runtime/bin/gh` and `.node-runtime/node/bin/node` had been extracted without their execute bit, which is why the JS test suite had silently not been running -- and it was still Helen's call to make, not mine.
- NEVER read, write or execute above the folder you're in.
- NEVER read, write or execute in `~` (my home directory) or anywhere outside this project folder, for any reason -- if Claude Code config/settings storage is ever needed, it belongs in this project's own `.claude/` folder, never `~/.claude/`.
- NEVER read, write or execute using the system `/tmp` directory (an absolute path starting `/tmp`). Use this project's own `tmp/` folder for all scratch and temporary files. Settings-level deny rules block this for the Read/Write/Edit tools, but Bash can't be perfectly path-restricted by permission patterns -- this rule is the actual backstop.
- NEVER use `$CLAUDE_JOB_DIR` or any path under `/home/helen/.claude/jobs/` as a scratch location, even though background-job tooling suggests it by default. All scratch/temporary files -- including any helper script written to a file specifically to avoid a shell-quoting/brace-expansion warning -- belong in this project's own `tmp/` folder, always.

## Git workflow
- If we're starting new work, and we're currently on main, please check out a new branch.
- **Update `main` WITHOUT checking it out: `git fetch origin main:main`.** This fast-forwards the local `main` ref while you stay on your working branch, so you are never standing on `main` and can never accidentally write to it. It refuses rather than mangles anything if the update is not a clean fast-forward, which is the signal that someone has committed locally to `main` and it needs a human. This replaced `git checkout main && git pull origin main` on 2026-08-20, after a commit landed on `main` in the gap that pattern opens.
- Commit freely without asking.
- **NEVER commit or merge directly onto `main`, for any reason, even a one-line fix or an untangle/cleanup task.** **A hook now enforces this** -- `.claude/hooks/guard-main-branch.py`, wired as a PreToolUse hook on Bash in `.claude/settings.json`, refuses `git commit` and `git merge` whenever the target repo is on `main`. It reads any leading `cd <path>` out of the command so it asks about the RIGHT repo (the nested drafts repos are edited through `cd _food_drafts && git ...`), and it strips quoted spans and heredoc bodies so a commit message may still discuss these commands. Everything else on `main` is untouched: reading, fetching, branching, checking out, pushing an existing commit. Added 2026-08-20, the day the written rule below was read and broken anyway.
- **THE AGREED WORKFLOW, settled 2026-08-20. Four steps, and only one is Helen's.**
  1. Claude works on a branch and pushes it (with Helen's confirmation, see below).
  2. **Helen opens the PR, reviews it, merges it. That is all she does.** No local checkout, no pull, nothing else.
  3. Claude runs `git fetch origin main:main` to fast-forward local `main` without leaving its branch, deletes the merged branch local and remote, and branches afresh for the next piece.
  4. Repeat. Claude is never on `main`, so the hook above should never actually fire.

  Helen is welcome to pull locally if she wants to -- it is a fast-forward either way and cannot conflict with step 3. The point is that nothing REQUIRES her to, because the old pattern (she merges, checks out `main`, pulls, and Claude carries on assuming the old branch) is what opened the gap. `main` only ever moves via a merged PR, never a direct local write.
- **Say when you have merged, if it is easy.** Not for correctness -- step 3 discovers it anyway -- but a merge changes which branch is current, and being told beats finding out. Equally: if Claude has been told nothing, it should check rather than assume.
- **This applies to EVERY repo in the working tree, not just `helen-triages`.** The nested private drafts repos (`_food_drafts/`, `_cocktail_drafts/`) are separate repos with their own `main`, and the same rule governs them: branch, never commit to `main`. Got this wrong on 2026-08-17 -- four commits went straight onto `_cocktail_drafts`' `main` because the rule read as if there were only one repo. They were moved to a branch and `main` reset to `origin/main`; nothing had been pushed.
- **NEVER run `git reset --hard` (or `git checkout --` / `git restore` over a dirty tree, or `git clean -fd`) without asking me first, every single time.** **A hook now enforces this** -- `.claude/hooks/guard-destructive-git.py`, wired as a PreToolUse hook on Bash in `.claude/settings.json`, refuses these commands whenever `git status` is not clean, and names what would be lost. It deliberately allows them on a CLEAN tree (a no-op is not dangerous, and a guard that fires on harmless invocations teaches you to route around it) and ignores quoted mentions and heredoc bodies, so a commit message may still discuss them. **It caught `git checkout <path>` only from 2026-08-19 onwards** -- the first version patterned the `git checkout -- <paths>` form alone, and the bare-path form walked straight past it and destroyed a file's uncommitted work the same day. Telling a path from a branch cannot be done by pattern (`git checkout main` is harmless, `git checkout feat/thing` looks exactly like a path), so it now asks the filesystem whether the argument names a real file. Added 2026-08-19 because this written rule was read and then broken the same day: an agent ran `git checkout -- <two files> 2>/dev/null || true` to undo its own edit and discarded work with it. The lesson generalises and is the reason the hook exists rather than a firmer sentence: a rule I read and break needs enforcement, not rewording -- the same conclusion this repo already reached about `meta.awaiting_fix` and `meta.proofread`. These discard uncommitted work with no undo and no reflog entry to recover it from. Ask, name what will be lost, and wait. Got this wrong on 2026-08-18: I ran `git reset --hard origin/main` to move a commit off `main` and silently destroyed a half-finished handover edit sitting uncommitted in the same tree -- the commit was safe, the uncommitted work was not. **Check `git status` first and say what it shows.** If something needs discarding and I am not around, `git stash -u` instead: it is reversible.
- **Check `git branch --show-current` immediately before every `git commit`, IN A SEPARATE TOOL CALL.** Not at the start of the task, and not in the same shell command as the commit. This is how commits landed on `main` twice on 2026-08-18 -- and then again on 2026-08-20 by an agent that *did* run the check, in this shape:

      git branch --show-current      <- the check
      git add ...
      git commit -F ...              <- already done by the time it printed

  The check ran and printed `main` in the output of the call that had already committed. **A check that cannot stop the thing it is checking is a narration, not a check.** Run it, read the answer, then decide. The hook above is the backstop for when this is forgotten again, but the habit is what should make the hook redundant.
- Never `git push` without my explicit confirmation first. **EXCEPT `main` in the two PRIVATE drafts repos, where pushing is fine and needs no ask** -- stated 2026-08-29: *"Pushing to main in the private repos is fine."* Nothing in `_food_drafts/` or `_cocktail_drafts/` triggers a build, so a push there has none of the every-merge-is-a-deploy cost that shapes the workflow in this repo, and a commit of mine sitting unpushed on a local `main` exists in exactly one place, which is the real risk. **This does NOT relax the rule against COMMITTING or MERGING onto `main`** -- that still holds in every repo in the tree, the hook still enforces it, and Claude's own work in those repos still goes on a branch. `helen-triages` itself is unchanged: never push it without explicit confirmation.
- **ALWAYS tag issues in commit messages.** If a commit resolves a GitHub Issue, add a `Fixes #N` (or `Closes #N`) trailer for every issue it resolves; if it only advances or touches one, cite it in the body (`Towards #N`, `See #N`). GitHub auto-closes on `Fixes`/`Closes` once the commit reaches `main`. Do this at commit time -- while nothing is pushed a message can still be rewritten, but after a push it is fixed. When summarising work, list the issue numbers involved.
- **A bare `#N` only resolves within its OWN repository.** The nested private drafts repos have their own (empty) trackers, so `Towards #314` in a commit there links to nothing. Cross-repo references need the full form: `Towards DeckOfPandas/helen-triages#314`.

## Proofreading -- Helen is the last judgement before a recipe publishes
- **If you edit a recipe file, set `meta.proofread: false` in the SAME commit.** Issue #367. Helen proofreads every recipe by hand before it goes live; if Claude changes the file afterwards, her proofread no longer covers what is in it. This is not a formality -- `meta.awaiting_fix` and `meta.proofread` are what the publish gate (#331) and the index badges hang off.
- **THE GATE IS TWO FLAGS AND IT FAILS CLOSED: a recipe or drink publishes only if it says `awaiting_fix: false` AND `proofread: true`.** Both, on both sites, since 2026-09-02 (#667, Helen's ruling D3 -- proofread "is the very last touch that I, the human, make to the file"). Not "true hides it" -- an explicit pass on both is the only thing that lets a page through. Either flag missing, the old hyphenated `awaiting-fix`, or a quoted string: all held back, and all break a test, which stops the build (#369). Never write the hyphenated form: Liquid parses `page.meta.awaiting-fix` as SUBTRACTION, so a template asking whether a page is flagged gets arithmetic and publishes it. The mechanism is `_plugins/publish_gate.rb` (called `hide_awaiting_fix.rb` until the second flag joined), and its build-log line names which flag held each page back.
- **It applies to any change to the file, including ones that look safe.** On 2026-08-18 twelve proofread recipes were edited in one commit (a wording change to eight of them, a note added to two, an ingredient group renamed) and not one flag was touched. Nothing noticed, because nothing was looking.
- `tests/test_front_matter.py::test_agent_edited_recipes_are_not_marked_proofread` enforces it by reading git history: if a recipe's newest commit carries a `Co-Authored-By: Claude` trailer, the file must say `proofread: false`.
- **The exception, and it is Helen's to grant, not yours.** If she has reviewed the change herself -- line by line, as she did for the 45 second-person edits on 2026-08-18 -- then she was the last judgement even though an agent's commit wrote the bytes. In that case move `BASELINE_COMMIT` in that test forward and say so in the commit message. Never move it to make a red test go green.

## GitHub Issues -- read/write, and nothing else
- **Changed 2026-08-17.** This used to say read-only, always. Claude may now READ, RAISE, CLOSE, REOPEN, COMMENT ON, LABEL and ASSIGN issues on `DeckOfPandas/helen-triages`, `helen-triages-food-private` and `helen-triages-cocktails-private`, using the fine-grained token I supply via the `GH_TOKEN` environment variable. Those three repositories and no others.
- **Verified by measurement on 2026-08-17, not assumed** -- issues: raise 201, comment 201, assign 201, label 200, close 200. Everything else refused: writing a file 403, reading Actions secrets 403, commenting on a pull request 403, opening a pull request 403. Re-run those probes if the token is ever regenerated; a widened token is invisible until something unexpected succeeds.
- **`GET /user/repos` DOES NOT REVEAL A FINE-GRAINED TOKEN'S SCOPE.** It lists what the account owns -- all 59 repos -- regardless of which three the token selected, and reading that as the token's reach produced a confident, wrong report that the token covered everything. The honest probe is a permission-requiring call against a specific repo, or Helen's own token settings page, which lists the selected repositories outright.
- **That is the entire permission.** Never push code, never open or merge a pull request, never change repository settings, secrets, Actions, webhooks or collaborators, and never act on any other repository. The token is scoped so these are impossible; do not treat a 403 as a problem to route around.
- **Never attempt to broaden access.** No `gh auth login`, no requesting a wider token, no suggesting a classic token, no adding scopes. If something genuinely needs a permission the token lacks, say so and stop -- I will do it by hand.
- **Never print, echo, log or commit the token**, and never write it into a file in this repo. Read it from the environment at the point of use.
- **CLOSE AN ISSUE WITH A COMMIT TRAILER, NOT THE API, WHENEVER A TRAILER CAN DO IT. This is a standing preference, stated 2026-08-29:** *"Close #540 (via commit message if possible -- this is always my preference)."* A `Fixes #N` / `Closes #N` trailer ties the closure to the commit that earned it, so the issue's history shows what actually resolved it instead of a bare "closed" with no link to the code. Reach for the API only where a trailer genuinely cannot work -- the clear case being work done in one of the nested private drafts repos, since a cross-repo trailer from a private repo does not close or even cross-reference a public issue (see the trap on this below).
- Closing an issue is still a real action on a shared, outward-facing thing: say which issues you are about to close and why before doing it, unless I have just told you to close them. That applies to a trailer too -- name the issues a commit will close before pushing, while the message can still be rewritten.
