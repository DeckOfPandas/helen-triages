{% comment %} ── THE PAGE'S FURNITURE LINE: the back arrow, and the search box ── Issue #387 (the arrow), #1024 (the search box, 2026-09-14) and #1050 (the search for anything, 2026-09-15). A row at the top of every recipe and drink page: the arrow at its left end returning to the index it came from, a search box at its right end that searches THIS site. Helen's placement for the box, from the candidates page: "back arrow's line, but on the right not in the centre." THE ARROW IS A REAL LINK FIRST, AND AN ENHANCEMENT SECOND, which is the whole design. The href points at this site's own index (from _data/sites.yml, so a cocktail goes back to /cocktails/ and a recipe to /food/) and works with no JavaScript, from a bookmark, from a search result, anywhere. assets/js/back-link.js then upgrades it to history.back() -- and ONLY when it can prove you actually arrived from that index. WHY history.back() RATHER THAN REBUILDING THE INDEX FROM A URL. Helen asked whether this could avoid a refresh "so the index page has the same recipe list I left it with", and the deciding fact is the shuffle: with no filters set the index reshuffles on every fresh load (MANUAL 13.7). So a link that rebuilds the index from a query string -- even a perfect one carrying every filter -- hands back a correctly filtered list in a DIFFERENT ORDER, which is not the list she left. Going back through history restores the page from the browser's cache instead: filters, page number, shuffle order and scroll position all intact, because the page was never re-rendered. THE SEARCH BOX IS A PLAIN FORM FIRST, AND IT WORKS WITH NO JAVASCRIPT. A GET to the index with `q=`; assets/js/filter-state.js's `parseName` reads it and each index puts the text into its own I KNOW WHAT I WANT box and applies it. Pressing Enter, or the magnifying glass (a real submit button), does exactly that. That was the whole of #1024. THE GLASS MOVED TO THE RIGHT END -- #1056, reversing #1050's own layout on seeing it built. It is now AFTER the input in the markup, which is also the natural tab order (type, then reach the submit control). §13.13's principle -- "the input is right-aligned so the text grows towards the glass" -- is applied again rather than dropped: with the glass now on the right, the input's text is LEFT-aligned, so what you type still grows towards the glass, only now from the box's left edge rightwards instead of the other way round. THEN assets/js/page-search.js MAKES IT A SEARCH FOR ANYTHING -- #1050. As you type, a dropdown under the box offers what the word could mean on this site, grouped by kind and in the index's own order: a recipe or drink by name first, then the star ingredients, moods, practicalities or hassles, then the ingredients. Each result is a real link -- to the page, or to the index already filtered by that word (`?star=`, `?tag=`, `?mood=`, `?ing=`, the grammar in filter-state.js). What it searches is this site's search.json, fetched the first time the box takes focus; `data-search-index` says where. The dropdown element is rendered here, empty and hidden, so the no-script page is exactly this page minus the script. THE GLASS IS HELEN'S OWN ARTWORK, _includes/icons/search.svg -- SVG Repo's "Interface / Search_Magnifying_Glass", pasted into #1050 -- redrawn to the site's icon contract the way icons/arrow-right.svg is: no fixed width or height, `currentColor` for the stroke so it takes the button's colour and hover, and a `class` parameter. The 800px canvas and the black stroke of the original were the repo's export settings, not the design. The partial carries no comment of its own because a Liquid tag inside an SVG file is not XML, and test_every_shipped_svg_actually_parses reads the file as XML.
